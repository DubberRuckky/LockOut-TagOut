The gateway's security decisions never depend on the app being reachable (it denies when unsure).

SECURITY MODEL
Login factors:
1. Device key: ed25519 signature over the nonce, plus the device config hash (existing).
2. Officer passcode: Argon2id hash stored in store.json, checked at login, set with lotoctl user add --passcode (hidden prompt), never logged.
3. Face presence (below).
The browser holds the keyfile in memory only (loaded with a file picker), never stored.
Ranks: tier 1 Constable, 2 Head Constable, 3 Sub-Inspector, 4 Inspector, 5 Superintendent. Stored in store.json, set with lotoctl user add --rank-tier N, passed to the app as X-Rank-Tier.
Lockout protocol (device level): three wrong credentials in a row on one device (bad signature, bad passcode or wrong config hash) lock THAT DEVICE until an admin runs lotoctl device reset <device_id>. This survives restarts and never changes the system-wide state. A face-check failure counts only against that device's rate limit.
System lock (LOCKED: 503 on everything except GET /status): triggered by a true replay of an accepted code, lotoctl lock, or tagout. RESTRICTED (read-only /api/*) is kept for three bad codes in one session, and that session is also ended.
Tagout protocol (investigation): an officer of rank tier 4 or higher (a constant at the top of the file) triggers it through an authenticated POST /api/tagout from the UI or through lotoctl tagout. Effect: all sessions end; the state becomes TAGOUT (a LOCKED variant recording initiator and time); the gateway answers 503 to everything except GET /status; the app is sealed; the UI shows a tagout screen. Only a terminal on the server host works (lotoctl); nothing is reachable over the network.
Restore from LOCKED or TAGOUT: lotoctl restore --restore-key <file> --officer-keyfile <a> --officer-keyfile <b>. The two officers must be different and tier 4 or higher; the restore token is valid for 2 minutes. On success the gateway calls unseal on the app. One approver, the same officer twice, or an expired token must fail.
Lock persistence: write the lock atomically. If saving fails when entering LOCKED, retry in the background and log loudly. After first-run initialisation writes lock-state.json (NORMAL), a missing lock file means LOCKED.
Sessions expire after a maximum age of 8 hours (a constant) and their number is capped. /ws requires the gateway token or carries no device ids (choose the simplest).
Face presence at login:
- Gateway route POST /auth/face {device_id, nonce, frames: [base64 JPEG, max 8, each max 200 KB, whole body max 1.5 MB]}. Only for a known device and a valid unused nonce; otherwise the same generic failure and NO call to the app. Max 3 face attempts per nonce plus a per-device rate limit. The nonce lives 90 seconds when face is required. On success the nonce is marked face_ok with a capture_id. Replies {ok:true} or {ok:false, reason} where reason is only no_face, blocked or try_again.
- /auth/login requires face_ok when LOT_REQUIRE_FACE=1 (default 1; 0 only in tests), else a generic 401.
- The gateway calls POST /internal/face-check through rustPolish.py. If the app errors or is unreachable, deny.
- candyWrapper.check_face(frames, nonce, device_id, officer_id) returns {ok, reason, face_count, frames_with_face, capture_id}. Blocked = a near-black or near-uniform frame. Face = OpenCV's bundled Haar frontal-face cascade, face height at least 15% of frame height, found in at least 3 frames. More than one face is allowed but flagged in the audit.
- Always store the best frame, encrypted at rest (AES-GCM, key from an environment variable or a key file outside the repo), with a database row: capture_id, ts, device_id, officer_id, nonce_hash, verdict, image_sha256, retention_until, hold. Delete failed-attempt images after 30 days (constant) unless a lockout or tagout holds them. get_capture(capture_id, requester, reason) is for tier 4 and up, and every access is an audit event. Purge at startup and daily. Only record for known device ids.
- The audit entry holds capture_id and image_sha256 only, never the image.
- Known limit, written in the README: this is presence only, not identity or liveness; a photo can pass. The login screen shows "Your face image is recorded for security audit and kept for 30 days."
